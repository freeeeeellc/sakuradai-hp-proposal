# 桜台自治会.com 改善提案

調査日 2026-08-04 ／ 根拠データは `01_サイトマップ.md` と `_audit/` を参照

---

## 結論を先に

このサイトの問題は「デザインが古い」ではない。**構造が2000年代前半のままで、住民がスマホで情報にたどり着けない**こと。
そして**252ページ中230ページが2024年7月28日で止まっている**のに、生きている情報（回覧板・議事録）と同じ重みで並んでいること。

直すべき順番は明快で、
**① 壊れているものを直す（1週間・ほぼ無料）→ ② スマホ対応と情報整理（本命）→ ③ 更新が続く体制（ここが本当の課題）**。

## B. 構造上の問題（作り直しが必要な部分）

### B-1. フレームセット構成 ← 最大の問題
`index.html` が `<frameset>`。HTML5で廃止された仕様で、実害が3つある。

1. **URLが共有できない。** 「防災訓練の回覧を見て」とLINEで送りたくても、個別ページのURLを送るとメニューも見出しも無い裸のページが開く。逆にトップのURLを送ると「そこから自分で探して」になる。**自治会の情報伝達手段として致命的。**
2. **検索から来た人が迷子になる。** Googleは中身のページを直接インデックスするので、着地点にナビゲーションが無い。
3. 印刷・ブックマーク・戻るボタンが期待通り動かない。

### B-2. スマホ非対応（252ページ中 viewport指定 **0ページ**）
左メニューが251px固定＋右が可変のため、375px幅（iPhone）では**必ず横スクロール**になる。実機幅で開くと800px相当で描画され、文字は指で拡大しないと読めない。
自治会の主な読者は住民＝スマホが中心。しかも高齢者比率が高い地域なら、**文字の小ささは即座に「読まれない」**に直結する。

### B-3. 情報が全部PDF（2,740本）
回覧板2,252本、広報誌275本。中身がHTMLに一切無いため、

- サイト内でもGoogleでも「ごみ 出し方」「夏祭り 日程」で**引っかからない**
- スマホでPDFを開くのは重い（実測で最大600KB超のPDFあり）。ページ自身も「PDFなので画面展開に少し時間がかかる場合があります」と注意書きしている

### B-4. 生きている情報と死んだ情報が同列
メニュー14項目のうち、実際に更新されているのは3項目（回覧板・自治会ファイル/議事録・生活情報の一部）。
残りはカレンダー（2018年11月で停止・97ページ）、イベント（2012年で停止・44ページ）、みんなの広場（2013年で停止・32ページ）。
**訪問者は「更新されていないサイト」と判断して離脱する。**

### B-5. 基本的なSEO要素が全滅
- `meta description`: **0ページ**
- `<h1>`: 実質0ページ（見出しは全部 `<FONT size="+2">`）
- `<title>` が「Left 目次」「Top 表題」のような内部用語のまま
- カレンダー97ページ全部が同じtitle「自治会カレンダー」／開花情報20ページも全部同じtitle

### B-6. 保守が属人化している
生成ツールが Homepage Builder 9.0 / 12.0 / 17.0 の3世代混在。`<FONT>`タグ・レイアウトテーブル・`bgcolor` で組まれ、一部ページには入れ子が23重になった `<font>` タグがある。
文字コードも Shift_JIS 232ページ／UTF-8 20ページの混在。
**「ホームページ作成委員会」の担当者が抜けた瞬間に更新が止まる構造。** 実際、2024年7月28日で230ページが一斉に停止しているのはその兆候に見える。

## C. 改善プラン

### フェーズ0：今週できる応急処置（コストほぼゼロ・現サイトのまま）
| 施策 | 内容 |
|---|---|
| 0-1 | 死んだトラッカー2本（web-cockpit / ga.js）を全ページから削除 → **GA4を設置**。以降は数字で判断できる |
| 0-2 | `sitemap.xml` を現ドメインのみで再生成（254件の死URLを除去）＋ `robots.txt` を設置 |
| 0-3 | 旧ドメインリンク12本を修正 or 削除（8ページ） |
| 0-4 | www → 非www の301統一、`<link rel="canonical">` 付与 |
| 0-5 | テストページと重複ページを非公開化 |
| 0-6 | アクセスカウンターをhttps化 or 撤去 |

> ここまでで「壊れている」状態は解消。ただし**スマホで読めない問題は残る**。

### フェーズ1：ホームページ本体の作り直し（本命）
1. **フレームセット廃止。1ページ＝1URL の通常HTMLへ。**
   共通ヘッダー／ハンバーガーメニュー／パンくずを各ページに持たせる。
   旧URLからは301リダイレクトで受ける（既存の被リンク・印刷物のURLを殺さない）。
2. **レスポンシブ化。** viewport指定、本文16px以上、行間広め、リンクは指で押せる大きさ（44px以上）。高齢者向けに文字サイズ変更ボタンも検討。
3. **トップページを「今日必要な情報」に組み替える。**
   ```
   ① 最新の回覧板（3件・日付つき）
   ② ごみ収集カレンダー
   ③ 自治会館の案内・予約
   ④ 緊急連絡先／防災
   ⑤ 今月のイベント
   ─────（以下、下層）
   自治会について／議事録・会計／広報誌バックナンバー／アーカイブ
   ```
4. **回覧板を「タイトル＋要約テキスト＋PDF」の形に。**
   最低限、既存のHTML一覧に入っている見出し文（例：「夏祭りによる休館のお知らせ」）を検索対象にするだけで大きく変わる。過去分の遡及は不要、**新規分から**でよい。
5. **サイト内検索を設置。**
6. **停止コンテンツはアーカイブへ集約。**（カレンダー2011-2018、イベント2006-2012、みんなの広場2013 → 「これまでの桜台」1ページに集約）
7. **titleとdescriptionを全ページ整備。**

### フェーズ2：更新が続く体制（ここが本当の勝負）
技術的に直しても、**更新する人がいなければ2年後に同じ状態に戻る。** 実際そうなっている。

**前提の確定：運用は自治会の方が行う。** これで技術選定が決まる。

#### 結論：WordPress（現行のXSERVERのまま）
| 判断軸 | 理由 |
|---|---|
| 人が代わっても引き継げる | 日本語の情報量が圧倒的。役員交代後も自力で調べられ、いざとなれば**他の業者にも引き継げる**（ロックインしない＝自治会にとっての安心材料） |
| 導入が容易 | XSERVERの標準機能で1クリック導入。**サーバ移転が不要** |
| 更新頻度に耐える | 回覧板は2025年で185本＝**月15本ペース**。手作業HTMLでは続かない量 |
| 「回覧板を1本追加」が3クリック | 入力項目を**日付・タイトル・PDF・1行説明の4つだけ**に絞った専用フォームを用意する |

**却下：静的サイト＋フォーム更新。** 安全で安価だが、仕組みを作った人がいなくなると誰も直せない。
**今と同じ失敗を繰り返す**ため採らない。

#### 「壊さない」ための設計（自治会運用の必須要件）
- 担当者の権限は**「投稿者」に限定**。固定ページ・テーマ・プラグインは触れないようにする
- プラグインは**3つ以内**に絞る（増えるほど壊れる・重くなる）
- XSERVERの**自動更新とバックアップを有効化**。障害時は前日に戻せる状態にする
- 納品物に**画面キャプチャ付きの手順書＋操作動画**を含める。役員交代時はこれを渡すだけで済む形にする

#### 追い風になる材料（調査で判明）
- 自治会は**「パソコン相談室」と「パソコン教室」を自前で運営**している（`/chiiki_katudou/PC_soudansitu.html`、`HP_iinkai/pc_school/`）。**中にIT寄りの人材がいる**
- **SKP（桜台自治会改革プロジェクト／2021年11月〜2022年11月）** の添付資料に「**回覧板の見直し**」「**専門事務員の制度設計**」「自治会改善ボランティアの制度設計」がある。
  → **HP刷新はSKPの続きとして提案できる。** 自治会自身が既に「今のやり方では続かない」と結論を出している

#### 併せて設計するもの
- LINE公式アカウント／オープンチャットとの併用（紙の回覧が届かない層への到達）。**パソコン相談室・パソコン教室を使った登録支援**とセットにすると定着する
- メール配信（`mail_haishin.html`）の現状確認と再設計。LINEと役割が重複するなら片方に寄せる

## D. 着手順の推奨

```
第1週  フェーズ0を全部やる（GA4含む）＋ 現状のヒアリング
第2〜3週 フェーズ1の設計（サイトマップ再設計・トップ構成案・デザイン方針）
第4週〜 フェーズ1の実装（まずトップ＋回覧板＋ごみ＋自治会館の4本）
その後  残りのページ移行 → アーカイブ集約 → フェーズ2の運用設計
```

「全252ページを一度に移行」は非現実的かつ無意味。
**生きている22ページを先に新サイトへ移し、残り230ページはアーカイブとして後追い**が正しい。

## E. 前提の確定と、残る確認事項

### 確定した前提（2026-08-04）
| 項目 | 回答 | 設計への影響 |
|---|---|---|
| 進行状況 | **まだ提案段階** | 成果物は「実装」ではなく**提案が通るための材料**。→ `03_さくらサービスセンター連携設計.md` |
| 納品後の運用 | **自治会の方が行う** | **WordPress で確定**（上記フェーズ2） |
| 課金モデル | 考慮不要 | 本書では扱わない |

### まだ確認が必要なこと
1. **サイトの目的の優先順位** — 住民への情報伝達か／自治会加入の促進か／活動記録の保存か。トップの構成が変わる
2. **更新担当は具体的に誰か** — ホームページ作成委員会の現在の人数と年齢層。手順書の詳しさが変わる
3. **役員の入れ替わり周期** — 1年交代なら「引き継げる仕組み」が最優先要件になる
4. **既存URLの扱い** — 印刷物や他サイトから貼られている旧URLがあるか（301の設計に必要）
5. **民生委員ページの現任者情報**（A-10）— 掲載を続けるか、自治会代表電話に一本化するか
